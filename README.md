# robot-dev-diary — 로봇 개발 A to Z

> 서빙로봇 위에 앱을 얹던 개발자가, SDK 아래층(자율주행 스택·멀티로봇)을 직접 구현하며 로봇 개발자가 되어가는 공개 일기.
>
> A public build-in-the-open diary: from zero robotics and zero C++ to a hand-built autonomy stack — mapping, localization, planning, Nav2 plugins, and multi-robot orchestration. No prior robotics or C++ assumed. Korean first; English summaries per chapter as they mature.

## 이 로드맵은 누구를 위한 것인가

- **로봇공학이 아예 처음인 사람** — 학위도 사전지식도 전제하지 않는다. 로봇이 어떻게 움직이는지부터 시작한다
- **C++이 처음인 사람** — 프로그래밍 자체가 처음이어도 따라올 수 있게 설계했다. 예제가 전부 로봇이라 지루할 틈이 없다 (다른 언어 경험자는 Part 1을 압축해서 빠르게 통과하면 된다)
- 로봇 SDK(제조사 API)를 *사용*해봤지만, 그 아래에서 무슨 일이 일어나는지 직접 만들어보고 싶은 개발자

전제: 로봇 지식 0, C++ 경험 0, 주 10–15시간, 약 12–15개월. (프로그래밍 유경험자는 Part 1을 2–3주로 압축해 ~12개월 페이스)

## 다섯 가지 규칙

1. **모든 코드는 손으로 타이핑한다.** 복사-붙여넣기, 생성 코드 금지. 이해하지 못한 줄은 커밋하지 않는다.
   - AI 사용 정책: 설명·리뷰·디버깅 질문은 적극 활용(과외 선생 모드), 인라인 자동완성과 코드 생성은 Part 4(맨손 자율주행) 완주까지 금지. 문답에서 나온 개념 정리는 [docs/notes/](docs/notes/)에 쌓는다.
2. **naive-first.** 프로덕션 도구(slam_toolbox, AMCL, Nav2)를 쓰기 전에, 같은 문제를 조악하게라도 직접 구현한다. "내가 만든 것 vs 프로덕션"의 격차가 최고의 교재다.
3. **매주 일기 1편.** 성공담보다 막힌 지점과 삽질이 더 중요한 콘텐츠다. ([일기 템플릿](docs/journal-template.md))
4. **챕터를 끝내면 git tag를 단다** (`chapter-a`, `chapter-b`, …). 따라오는 사람은 태그 단위로 체크아웃한다.
5. **커지면 졸업시킨다.** 챕터 산출물이 독립 프로젝트가 되면(시뮬 월드, fleet adapter 등) 별도 레포로 분리하고 여기서 링크한다.

## Part 0 — 준비 (1주)

### A. 개발 환경 구축
macOS(Apple Silicon)에서 ROS 2는 네이티브 지원이 없다. Docker 컨테이너(Ubuntu 24.04 + ROS 2 Jazzy)를 기본 무대로, VS Code Dev Containers로 개발한다. 시각화는 헤드리스 시뮬 + Foxglove로 우회하는 게 맥에서 가장 쾌적하다.
- 만들 것: 재현 가능한 개발 환경 — `Dockerfile` + `devcontainer.json`, C++ hello-world ROS 2 노드가 컨테이너에서 빌드·실행
- 완료 기준: 새 맥북에서 30분 안에 같은 환경을 재현할 수 있는 문서 ([docs/setup-macos.md](docs/setup-macos.md))
- 일기 포인트: "로봇 개발의 첫 관문은 로봇이 아니라 리눅스였다"
- 학습 노트: [C++/ROS 2 툴체인의 큰 그림](docs/notes/chapter-a-toolchain.md) — colcon·CMake·make/ninja·g++·clangd·rcl/rclcpp·ament의 관계 총정리

## Part 1 — 로봇공학 입문과 C++ 첫걸음 (4–6주)

> 목표: 코드보다 개념이 먼저다. 로봇이 어떻게 움직이는지 큰 그림을 잡고, 그 세계를 표현할 언어(C++)를 밑바닥부터 익힌다. 프로그래밍이 처음이어도 여기서부터 따라오면 된다.

### B. 로봇공학 첫 지도 — 로봇은 어떻게 움직이는가 (1주, 코드 없음)
모든 로봇은 하나의 루프다: **센서(감각) → 컴퓨터(판단) → 액추에이터(행동)**, 초당 수십 번. 그리고 자율주행은 네 단계 파이프라인이다: **인지 → 위치추정 → 계획 → 제어**. 이 로드맵 전체가 이 지도의 확대판이라는 걸 먼저 본다.
- 배울 개념(수식 없이 그림으로): 포즈(x, y, θ)와 헤딩, 좌표계(지도/로봇/센서), 오도메트리, 차동구동, 그리고 **HAL(하드웨어 추상화 계층)** — 뇌(제어 코드)와 몸(모터·센서) 사이의 계약이라는 아이디어
- 센서 카탈로그: 휠 엔코더, IMU, 2D LiDAR, 깊이 카메라, 범퍼 — 각각 무엇을 재고 무엇을 못 재나
- 실습: 주변의 로봇(식당 서빙로봇, 로봇청소기)을 관찰 해부 — 센서 위치를 찾고, "지금 파이프라인의 어느 단계를 돌고 있나" 추측해서 기록
- 산출물: 로봇 해부도 1장 + 자율주행 파이프라인 지도 1장 + 내 언어로 쓴 용어집
- 완료 기준: "호출 벨이 울리고 로봇이 테이블에 도착하기까지 내부에서 일어나는 일"을 비전공자에게 5분간 설명할 수 있다

### C. C++ 첫걸음 — 값·함수·흐름을 로봇 예제로 (1–2주)
변수와 타입(int/double/bool/std::string), 함수, if/for, std::vector와 범위 for. 교재는 [learncpp.com](https://www.learncpp.com)을 따라가되, 연습은 전부 로봇 미니 함수로 한다: 배터리 부족 판정, 속도 명령 클램핑, LiDAR 스캔 평균 거리, 미터↔셀 변환.
- 빌드는 g++ 직접 호출로 — 컴파일러와 맨몸으로 먼저 만난다 ([노트 §1-1](docs/notes/chapter-a-toolchain.md) 연결)
- 완료 기준: `g++ 파일.cpp -o 실행파일`을 스스로 다루고, 로봇 미니 함수 10개 이상 작성

### D. C++ 뼈대 — 클래스·포인터·수명, 그리고 HAL (2주)
struct/class로 Pose와 RobotState를 모델링하고, 참조와 포인터("복사인가 참조인가"), const 정확성, 스택 vs 힙과 수명, RAII·스마트 포인터 첫 만남, 헤더/소스 분리. 마지막으로 가상 함수와 추상 클래스로 **HAL 인터페이스**를 설계한다 — 뇌 코드는 몸이 시뮬인지 실물인지 몰라야 한다.
- 만들 것: ① 서빙로봇 상태 머신 — `IDLE → MOVING → ARRIVED → RETURNING` 전이와 불법 전이 거부 (실제 서빙로봇의 상태 전이 모델이 정확히 이런 모양이다) ② `RobotHAL` 인터페이스(`set_wheel_speeds` / `read_encoders`)와 그것을 구현한 `SimRobot` — Part 2 관통 프로젝트 `my-turtlesim`의 심장이 된다
- 완료 기준: "이 함수에 값을 넘길까 참조를 넘길까"를 근거를 들어 답하기 + "브레인 코드가 SimRobot이라는 타입을 몰라도 되는 이유"를 설명하기

### E. CMake와 테스트 장비를 맨손으로 (1주)
파일이 늘어나며 g++ 직접 호출이 고통스러워졌을 때가 CMake를 배울 순간이다. IDE 매직 없이 라이브러리+실행파일+테스트 3-타깃 프로젝트를 짜고, GoogleTest·clang-format·새니타이저(ASan/UBSan)를 붙인다. 첫 테스트 대상은 `deg2rad`/`wrap_to_pi` — Part 2의 채점기를 여기서 만든다.
- 만들 것: `part2/robomath` 스캐폴드 (이후 전 챕터의 기본 장비)
- 완료 기준: `cmake -B build && cmake --build build && ctest` 파이프라인의 각 단계를 남에게 설명 가능

## Part 2 — 로봇 수학 실전 (5–7주)

> 목표: 로봇 수학(삼각함수·벡터·행렬·연립방정식·변환)을 **실전 문제로** 손에 붙인다. 모든 문제는 실제 상용 서빙로봇 운영에서 매일 돌아가는 계산에서 가져왔다.
> **문제집: [서빙로봇 현장에서 온 로봇 수학 18문제](docs/problems/part2-robot-math.md)** — 문제마다 현업 맥락·테스트 케이스·힌트가 달려 있고, TDD로 푼다.
>
> **관통 프로젝트: `my-turtlesim`** — ROS의 turtlesim처럼, **직접 만든 함수로 움직이는 나만의 2D 거북이 시뮬레이터**를 함께 만든다. D장의 `RobotHAL`을 구현한 `SimRobot` 위에 렌더러를 얹고, 세트를 끝낼 때마다 거북이가 새 능력을 얻는다. 렌더링은 단계적으로 — 터미널 ASCII(F) → SVG 궤적 애니메이션(G–H). 외부 그래픽 라이브러리는 안 쓴다: ASCII는 `std::cout`, SVG는 텍스트 파일이다. 눈에 보이면 수학이 산다.

### F. 각도와 헤딩 — 삼각함수 실전 (1–2주)
atan2, 각도 정규화, 최단 회전각, 시야각 판정, 자이로 적분. "로봇이 테이블을 바라보려면 몇 도를 어느 방향으로 돌아야 하나"부터 시작한다.
- 만들 것: 문제집 **Set 1** 6문제 (constexpr, 타입 안전 각도) + **my-turtlesim v0** — 터미널 ASCII 렌더: 화살표 거북이(→↗↑)가 내 `shortest_turn`으로 최단 방향 회전하고 내 `bearing_to`로 목표를 향해 전진한다
- 완료 기준: 350°→10° 최단 회전이 +20°임을 코드와 **화면에서 도는 거북이로** 증명, atan vs atan2 차이 설명
- 일기 포인트: 자이로 바이어스 적분 실험 — 드리프트를 눈으로 목격

### G. 벡터·행렬·피팅 — 미니 선형대수 (2주)
Vec2/Mat2/Mat3(동차좌표)를 직접 만들고, LiDAR 점들로 벽 직선 최소제곱 피팅, 두 벽의 교점(연립방정식), 경로 이탈 거리(크로스트랙 에러)까지.
- 만들 것: 문제집 **Set 2** 6문제 → 자작 선형대수 헤더 + **my-turtlesim v1** — SVG 프레임 출력: 가짜 LiDAR 점들, 피팅된 벽 직선, 교점(코너)이 그림으로 그려진다
- 완료 기준: 최소제곱 정규방정식 유도를 주석으로 설명, 회전 합성=각의 합 테스트 통과
- 일기 포인트: Eigen을 아직 안 쓰는 이유 — 직접 만들어봐야 나중에 감사할 수 있다

### H. SE(2) 변환 체인과 오도메트리 — `libpose2d` 완성 (1–2주)
Pose2D 합성·역변환, 센서 마운트 캘리브레이션(지도←로봇←센서 2단 체인), 서빙 접근 포즈 계산, 엔코더→포즈 적분, world↔grid 변환과 레이캐스팅까지. Part 4(맨손 자율주행)의 수학이 전부 여기서 준비된다.
- 만들 것: 문제집 **Set 3** 6문제 → 헤더 온리 **`libpose2d` v1.0** + **my-turtlesim v2** — 펜 궤적: 오도메트리 추정 경로 vs 실제 경로의 드리프트가 두 색 선으로 보이고, 접근 포즈로 다가가 정렬하는 데모까지
- 완료 기준: "지도→로봇→센서" 변환 체인을 그림으로 설명 + 18문제 전 테스트 통과 + my-turtlesim 데모 화면 녹화
- 일기 포인트: 이 라이브러리는 K장에서 TF2에 명예롭게 은퇴당한다 — 그때 "TF2가 왜 필요한가"를 몸으로 안다

## Part 3 — ROS 2 기초 (6–8주)

### I. 노드·토픽·QoS (1–2주)
rclcpp로 퍼블리셔/서브스크라이버를 작성하고, QoS(reliability, durability, history)의 의미를 실험으로 확인한다. 도입부에서 스레드·뮤텍스·콜백 큐를 다루고 executor의 스레딩 모델과 연결한다.
- 만들 것: 가짜 로봇 — 속도 명령(`cmd_vel`)을 적분해 odom을 퍼블리시하는 C++ 노드 (H장의 `libpose2d`가 부품이 된다)
- 완료 기준: QoS 미스매치로 메시지가 안 오는 상황을 일부러 만들고 원인을 설명

### J. 서비스·액션·라이프사이클 (1–2주)
요청-응답(서비스), 장기 작업(액션), 관리형 노드(라이프사이클), executor와 콜백 그룹.
- 만들 것: "지점으로 이동" 액션 서버 — 가짜 로봇이 목표점까지 이동, 진행률 피드백
- 완료 기준: 주행 중 취소가 실제 정지로 이어지는 것을 보이고, 노드를 비활성화하면 진행 중이던 goal이 abort되고 자원이 그래프에서 사라지는 것을 `ros2 lifecycle`로 확인
- 일기 포인트: 상용 로봇 SDK의 navigation API가 사실 액션이었다는 것을 여기서 깨닫는다

### K. TF2 — 내 라이브러리를 은퇴시키기 (1주)
좌표 프레임 트리(map → odom → base_link → laser), 시간 보간, `tf2_ros` broadcaster/listener.
- 만들 것: Part 2에서 완성한 `libpose2d` 사용처를 TF2로 전면 교체 (문제 3-3 센서 캘리브레이션이 static transform 한 줄이 되는 순간)
- 완료 기준: "왜 map→odom이 별도 프레임인가"(위치추정 보정의 자리)를 그림으로 설명
- 학습 노트: [TF2 프레임 트리 — 왜 map→odom이 따로 있는가](docs/notes/chapter-k-tf-tree.md) — 3단 트리의 근거, 조회 실패 원칙, TF 디버깅 도구

### L. URDF로 로봇 정의하기 (1주)
차동구동 로봇의 링크·조인트·관성·센서 마운트를 URDF(xacro)로 기술, `robot_state_publisher` + RViz/Foxglove로 확인.
- 만들 것: 2륜 + 캐스터 + 2D LiDAR 구성의 내 로봇 모델
- 완료 기준: TF 트리와 모델이 일치

### M. Gazebo 시뮬레이션 (2주)
gz-sim에 URDF 스폰, 차동구동·LiDAR 센서 플러그인, ros_gz 브리지. 여기서 만든 월드가 이후 전 챕터의 무대다.
- 만들 것: 레스토랑풍 월드(테이블·통로) + 손으로 짠 C++ 텔레옵 노드
- 완료 기준: 키보드로 시뮬 로봇 주행, LiDAR 스캔이 토픽으로 흐름
- 졸업 후보: 이 월드는 커지면 `serving-sim` 독립 레포로 분리
- 은퇴식: Part 2의 `my-turtlesim`이 Gazebo에 자리를 물려준다 — 내가 만든 시뮬(운동 적분·렌더·시간 관리)과 프로덕션 시뮬(물리 엔진·센서 노이즈·플러그인)의 차이를 일기로

## Part 4 — 자율주행 원리를 맨손으로 (8–10주) ★ 이 일기의 심장

> 목표: 프로덕션 도구가 풀어주는 문제를 먼저 조악하게 직접 푼다. 면접에서 "AMCL이 왜 수렴하는지 그림으로 설명"이 가능해지는 구간. 확률(베이즈, 가우시안)은 O장에서 필요해진 순간에 배운다.

### N. 오도메트리 실전과 점유 격자 매핑 (2–3주)
문제 3-5의 `integrate_odom`을 시뮬 로봇에 물려 실주행 드리프트를 데이터로 관찰한 뒤, 알려진 포즈 가정 하에 LiDAR 스캔으로 log-odds 점유 격자 지도를 직접 만든다(레이캐스팅, 확률 업데이트).
- 만들 것: 주행하며 실시간으로 자라는 내 매핑 노드 (C++)
- 완료 기준: 오도메트리 오차 패턴 리포트 + 내 지도와 slam_toolbox 지도의 육안 비교

### O. 파티클 필터 위치추정 — MCL (2–3주)
모션 모델, 측정 모델(likelihood field), 리샘플링을 직접 구현해 N장의 지도 위에서 로봇을 위치추정한다. 베이즈 필터는 여기서 수식↔코드 한 줄씩 대응시키며 배운다.
- 만들 것: 파티클 구름이 수렴하는 과정을 시각화하는 MCL 노드
- 완료 기준: 납치된 로봇(kidnapped robot) 상황에서 재수렴 데모

### P. A* 전역 계획 (1–2주)
격자 지도 위 A*를 직접 구현, 휴리스틱·타이브레이킹·경로 스무딩까지.
- 만들 것: 지도 클릭 → 경로 생성 노드
- 완료 기준: 막힌 통로를 막았을 때 대안 경로가 즉시 나오는 데모

### Q. 경로 추종 제어기 (1–2주)
Pure Pursuit(또는 DWA 나이브 버전)로 P장의 경로를 실제로 따라가게 한다. 전방주시거리, 속도 프로파일, 장애물 앞 정지. (문제 2-4의 크로스트랙 에러가 핵심 입력값)
- 완료 기준: N~Q를 엮은 풀 파이프라인 — 내 지도 + 내 위치추정 + 내 플래너 + 내 제어기로 시뮬 로봇이 목적지 도달

### R. 프로덕션 스택으로 교체 — 그리고 비교 (1주)
같은 로봇·같은 월드에 slam_toolbox + AMCL + Nav2를 올리고, 내 구현과 성능·강건성·설계를 항목별로 비교하는 긴 일기를 쓴다.
- 완료 기준: "내가 만든 것은 어디서 부서지고, 프로덕션은 그걸 어떻게 푸는가" 비교표
- 이 일기가 이 레포의 대표 콘텐츠가 된다

## Part 5 — Nav2 제대로 (5–7주)

### S. Nav2 아키텍처·튜닝·Behavior Tree (2–3주)
BT Navigator, planner/controller/behavior 서버, costmap 레이어 구조, 파라미터 튜닝. M장의 레스토랑 월드에서 좁은 통로·동적 장애물 시나리오로 튜닝 근거를 문서화하고, BT.CPP로 커스텀 노드를 하나 작성해 동작 흐름을 바꿔본다(예: "혼잡하면 대기 후 재시도").
- 완료 기준: 파라미터 하나하나에 "왜 이 값인가"가 달린 튜닝 노트 + 기본 BT와 내 BT의 동작 차이 데모

### T. 커스텀 costmap layer 플러그인 (2–3주) ★ 킬러 산출물
C++로 pluginlib 기반 costmap layer를 저작한다. 주제: **human-aware etiquette layer** — 감지된 사람 주변에 감속·회피 비용 부여 (서빙로봇 현장 경험의 공개 버전).
- 완료 기준: 사람 접근 시 감속이 costmap 시각화로 확인되는 데모 + 영문 README

### U. 실물 하드웨어 포팅 — 하드웨어 트랙 (3–4주, 병행 가능)
RPLiDAR + SBC(Jetson/RPi) + 차동구동 베이스로 시뮬 스택을 실물에 올린다. 오도메트리 캘리브레이션, 센서 마운트 오프셋, 실환경 튜닝.
- 개념의 보상: D장에서 설계한 `RobotHAL`의 실물판을 만드는 장이다 — 업계 표준은 **ros2_control의 `hardware_interface`**(프로덕션 HAL). 같은 브레인 코드가 시뮬과 실물에서 도는 순간, "뇌와 몸의 계약"이 왜 계약인지 안다
- 완료 기준: 집/사무실 지도 작성 → 목적지 주행 → 사람 회피 영상
- 예산: 자작 약 60–70만 원 (시뮬만으로 V장 진행도 가능 — 늪에 빠지면 과감히 스킵)

## Part 6 — 멀티로봇 (8–10주) ★ 포트폴리오의 킬러 피스

### V. 멀티로봇 시뮬과 naive 트래픽 매니저 (2–3주)
네임스페이스로 로봇 3대 + 각자 Nav2 스택. 좁은 복도 교차 상황에서 데드락을 직접 목격한 뒤, 예약 테이블 기반 나이브 중앙 트래픽 매니저를 C++로 만든다.
- 완료 기준: 나이브 매니저로 데드락 해소 데모 + 한계 기록

### W. Open-RMF fleet adapter (3–4주)
RMF 개념(fleet adapter, traffic negotiation, task dispatch)을 익히고 내 시뮬 로봇용 fleet adapter를 작성한다. 문/리프트 mock 연동 1개 포함.
- 완료 기준: 로봇 3대가 1.5m 복도에서 데드락 없이 교차 통행 10회 연속
- 졸업 후보: fleet adapter는 독립 레포로

### X. 플릿 관제 대시보드와 SLO (2–3주)
라이브 관제 대시보드(디지털트윈)와 Prometheus 플릿 메트릭(미션 성공률, 협상 지연, MTTR).
- 완료 기준: 분할 화면(시뮬 + 대시보드) 3분 데모 영상

## Part 7 — 세상에 내놓기 (병행)

### Y. 업스트림 기여
Part 4–6에서 만난 문서 구멍·버그를 Nav2/Open-RMF에 되돌린다. 이슈 트리아지 → 문서 → 버그픽스 → 기능 순.
- 완료 기준: 머지된 PR 3개 이상 (최소 1개는 코드)

### Z. 쇼케이스 — 영문화·데모 릴·포트폴리오·회고
대표 챕터(R, T, W, X)의 영문 README, 데모 영상 자막, 2–3분 하이라이트 릴, 원페이지 포트폴리오 사이트, 그리고 이 일기 전체의 회고 — "제로에서 스택 빌더까지".
