## 은퇴식 - 내 시뮬 vs 프로덕션 시뮬

| | I장 `fake_robot_node` | Gazebo |
|---|---|---|
| `odom → base_link` | `integrate_odom` (운동학) | **동역학** (질량·관성·마찰) |
| 바퀴 회전 | 계산 안 함 | 실제 관절이 돎 |
| 정지 명령 | 즉시 멈춤 | **관성으로 미끄러짐** |
| 명령 대비 실제 | 100% | **92%** (가속 구간 손실) |
| 넘어짐 | 개념 없음 | **일어남** |

마지막 줄이 이번 장의 전부다. **내 시뮬은 로봇이 넘어질 수 있다는 걸 몰랐다.**

## 막힌 것 -> 어떻게 풀었나

- **`use_sim_time` - 시간이 두 개였다**: TF 스탬프가 `sec: 150` 인데 벽시계는 `1786943464`.
  데이터는 흐르는데 `tf2_echo` 는 "frame does not exist" 라고 했다. `/clock` 을 브리지하고
  **모든 노드에** `use_sim_time:=true` 를 줘야 했다 - `tf2_echo` 같은 CLI 도구까지 포함해서.
  **시뮬 시간과 벽시계는 다른 축이고, 한 노드라도 다른 축에 있으면 TF 조회가 실패한다.**

- **월드에 없는 플러그인은 없는 대로 돌아간다**: `empty.sdf` 에는 `Sensors` 시스템이 없어서
  라이다가 **아예 돌지 않았다**. 내 월드를 만들 때는 `Physics`/`UserCommands`/`SceneBroadcaster`
  까지 빠뜨려서 `gz service -l | grep create` 가 **0개**였다 - 스폰 자체가 불가능했다.
  에러도 경고도 없다. `gz service -l` / `gz topic -l` 로 **기대한 게 생겼는지 확인**해야 한다.

- **Gazebo 토픽 이름에는 월드·모델이 접두사로 붙는다**:
  - `/tf` 의 프레임이 `fake_robot/odom` -> DiffDrive 에 `<frame_id>`/`<child_frame_id>`/`<tf_topic>`
  - 조인트 상태는 `/world/empty/model/fake_robot/joint_state` (단수형!) -> 브리지에서 리매핑
  - 라이다 `frame_id` 가 `fake_robot/base_link/lidar` -> 센서에 `<gz_frame_id>laser</gz_frame_id>`
  **문서에 적힌 짧은 이름을 믿지 말고 `gz topic -l` 로 실제 이름을 확인한다.**

- **★ 로봇이 넘어져 있었는데 아무도 몰랐다**: 라이다 정면이 3.75m 여야 하는데 **0.92m** 가 나왔다.
  ```
  gz model -m fake_robot -p     ->  RPY [0, 0.153544, 0]   pitch 8.8° 앞으로 숙임
  ros2 topic echo /odom         ->  orientation w=1        완벽히 수평
  ```
  **오도메트리는 2D 라 pitch/roll 을 발행하지 않는다.** TF 트리도 3D 화면도 멀쩡했다.
  원인은 무게중심: 바퀴가 `x=0`, 캐스터가 `x=-0.15`(뒤) 라 지지 구간이 `[-0.15, 0]` 인데,
  라이다 0.2kg 이 `x=0.2` 에 매달려 **CoM 이 +0.004m** - 구간 밖이었다. 앞으로 넘어질 수밖에.
  캐스터를 앞뒤 2개로 만들어 지지 구간을 `[-0.15, +0.15]` 로 넓혀 해결했다.
  **이상을 잡아낸 건 손으로 계산해둔 기대 거리(3.95 - 0.20 = 3.75)였다.**

- **`switch` 폴스루로 종료됐다**: `s` 를 눌렀는데 노드가 죽었다. `case 's'` 에 `break` 가 없어서
  `'a'`, `'d'` 를 지나 `case 'q': rclcpp::shutdown()` 까지 흘러내려간 것.
  gcc 13.3 에 `-Wall -Wextra` 를 줘도 **경고가 없었다** (폴스루는 합법 문법이라 보수적).
  **증상(s 누르면 종료)과 원인(s 의 빠진 break)이 멀었다** - L장의 "3행 에러, 2행 원인" 과 같다.

- **DiffDrive 는 명령이 끊기면 멈춘다**: `ros2 topic pub --once` 로는 잠깐 움직이다 만다.
  텔레옵이 **20 Hz 로 계속 발행**해야 하는 이유. 내가 회전 시험을 대충 했다가
  "캐스터 마찰로 회전이 안 된다" 고 잘못 판단한 적도 있다 - **측정 방법이 틀리면 결론도 틀린다.**

- **화면 없이 그림 보기**: Dev Container 에 `DISPLAY` 가 없어 `gz sim` GUI 가 안 뜬다.
  월드에 **카메라 센서를 놓고** `/spectator` 를 Image 로 브리지해 Foxglove 에서 봤다.
  `--headless-rendering` 이면 화면 없이도 GPU 렌더링이 된다.
  지도 시점은 `<pose>0 0 16 0 1.5708 1.5708</pose>` - pitch 90°(수직 하방) + yaw 90°(북쪽을 위로).

- **SDF 는 URDF 와 문법이 다르다**:
  ```
  URDF:  <box size="0.4 0.3 0.1" />               속성
  SDF:   <box><size>0.4 0.3 0.1</size></box>      자식 요소
  URDF:  <origin xyz="..." rpy="..." />           두 개
  SDF:   <pose>x y z r p y</pose>                 한 줄 6개
  ```
  SDF 에는 `<material name="blue">` 같은 **이름 재사용이 없다** - `<visual>` 마다 색을 직접 적는다.

- **XSD 스키마 연결은 실패했다**: `redhat.vscode-xml` 에 sdformat 의 `root.xsd` 를 물렸더니
  오류가 났다. `root.xsd` 가 나머지를 **`http://sdformat.org` 에서 원격으로 include** 하고,
  `systemId` 는 워크스페이스 상대경로로 해석된다. 포기하고 `gz sdf --check` 를 쓰기로 했다.
  **실제 파서가 판정하는 게 스키마보다 정확하다.**

## launch 파일 - 손으로 6번 띄워본 뒤에 쓰니 다르다

L장 일기에 "일부러 손으로 해서 왜 launch 가 필요한지를 몸으로 익혔다" 고 썼는데, 그 답을 코드로 옮겼다.
손으로 겪은 것들이 그대로 launch 의 한 줄씩이 됐다.

```text
터미널 명령                            launch
────────────────────────────────────────────────────────────
ros2 run <A> <B>                      package='A', executable='B'
--ros-args -p k:=v                    parameters=[{'k': v}]
--ros-args -r a:=b                    remappings=[('a', 'b')]
그 밖의 인자                           arguments=[...]
gz sim ... (ROS 노드가 아님)           ExecuteProcess(cmd=[...])
"rsp 뜨고 5초 뒤에 스폰"               TimerAction(period=5.0, actions=[spawn])
```

- **`Node` vs `ExecuteProcess`** - `Node` 는 `--ros-args` 를 붙이고 ROS 이름·파라미터 규약을 적용한다.
  `gz sim` 은 그런 걸 모르므로 `ExecuteProcess`. **ROS 노드인가 아닌가**가 기준이다.
- **`ParameterValue(Command([...]), value_type=str)`** - 터미널에서 `$(xacro ...)` 를 셸이 해줬는데
  launch 에는 셸이 없다. `Command` 가 실행하고, `value_type=str` 이 없으면 URDF 를 YAML 로
  파싱하려다 터진다. `'xacro '` 뒤 **공백**을 빠뜨리면 `xacro/ws/...` 라는 명령을 찾는다(붙여쓴다).
- **`LaunchDescription` 의 나열 순서는 실행 순서가 아니다.** 전부 동시에 뜬다.
  순서를 만드는 건 `TimerAction`(또는 `RegisterEventHandler`) 뿐.
- **launch 파일은 파이썬이지만 "실행하는 코드" 가 아니다.** `LaunchDescription` 이라는 *계획서*를
  만들어 돌려주면 launch 시스템이 그걸 보고 프로세스를 띄운다. 그래서 `Node(...)` 를 만들어놓고
  리스트에 안 넣으면 **아무 일도 안 일어난다** - 이번 장에서 세 번째로 만난 그 패턴.
- **YAML 브리지 설정의 이득 두 가지**
  1. `ros_topic_name` 과 `gz_topic_name` 을 따로 써서 **리매핑이 필요 없다**
     (`/world/restaurant/model/fake_robot/joint_state` -> `/joint_states`)
  2. 방향이 `[`, `]`, `@` 기호가 아니라 `GZ_TO_ROS` 라는 **단어**라서, 읽다가 "이게 왜 양방향이지?"
     하고 의심하게 된다. 실제로 `/odom` 과 `/tf` 가 불필요하게 양방향이던 걸 이때 발견했다.

**launch 로 묶으니 새로 보인 것**: 터미널이 흩어져 있을 때는 묻혔던 경고가 한 화면에 모였다.
```text
[kdl_parser] The root link base_link has an inertia specified in the URDF,
             but KDL does not support a root link with an inertia.
```
Gazebo 는 `base_link` 의 관성이 **필요하고**, `robot_state_publisher` 의 KDL 은 루트 링크 관성을
**쓰지 않는다**. 같은 URDF 를 다른 목적으로 읽어서 생기는 마찰이다. TF 발행에는 영향이 없다.
더미 링크를 넣는 관례가 있지만, 의미 없는 링크 하나 늘리고 경고 하나 없애는 거래라 넘어갔다.
**"URDF 는 하나인데 소비자가 여럿" 이라는 L장 결론의 실제 모습.**

## 새로 배운 개념
- **RAII 를 직접 만들었다.** J장에서 `std::lock_guard` 를 *쓰기만* 했는데, 이번엔 생성자에서
  자원을 얻고 소멸자에서 되돌리는 클래스를 손으로 짰다. `Ctrl+C` 든 예외든 **소멸자는 불린다.**
  복사 생성자와 복사 대입을 **둘 다** `= delete` 해야 완전하다는 것도 배웠다(둘은 다른 함수다).
- **터미널 설정은 내 프로세스 것이 아니다.** 커널의 tty 장치에 붙어 있어서, 복원 안 하고 죽으면
  셸이 망가진 상태를 물려받는다. 그래서 "고정값으로 되돌리기" 가 아니라 **통째로 백업 후 복원**.
- **`gz service -l` / `gz topic -l` / `gz model --list` / `gz model -m X -p`** - Gazebo 의 진실을
  묻는 도구들. ROS 쪽만 보면 속는다(오도메트리가 수평이라고 우긴 것처럼).
- **설치된 예제가 최고의 문서다.** `gz-sim8/worlds/*.sdf` 수백 개를 `grep -l "gpu_lidar"` 로
  뒤지는 게 웹 문서보다 빠르고 정확하다 - 버전이 정확히 내 것과 맞으니까.

## 남겨둔 것
- **`TimerAction(period=5.0)` 은 임시방편이다.** `robot_state_publisher` 가 `/robot_description` 을
  발행한 뒤에 스폰해야 하는데, 근거 없는 5초로 때웠다. 느린 머신이면 실패하고 빠른 머신이면 낭비다.
  정석은 `RegisterEventHandler` + `OnProcessStart` 로 **이벤트**를 잡는 것. 동작은 하니 다음 기회에.
- **`/joint_states` 가 1002 Hz, `/clock` 이 1014 Hz.** 물리 스텝(1ms)마다 발행한다.
  `/scan` 이 10 Hz 인 걸 생각하면 100배다. `JointStatePublisher` 플러그인이 받는 태그는
  `topic` 과 `joint_name` 뿐이라 **속도 제한 옵션이 없다.** 지금은 RTF 1.0 으로 잘 도니 둔다.
  월드가 커지거나 로봇이 여러 대가 되면 브리지 부하로 나타날 것 - **측정해두고, 아프면 그때 고친다.**
- `track` 값이 URDF 와 C++ 코드 두 곳에 있다 (L장에서 넘어온 숙제, 아직 그대로).
- 관전 카메라가 **1 Hz** 밖에 안 나온다. GPU 가속이 없어 소프트웨어 렌더링이라 그렇다.
  해상도를 320x240 으로 줄여 완화했지만 근본 해결은 아니다.
- `robomath/src/grid.cpp` 에 C++20 지정 초기화자 경고 - `-Wall -Wextra` 를 켜자마자 나왔다.
  Part 2 코드라 지금은 두지만, **경고를 켜자마자 몰랐던 게 하나 나온다**는 게 요점.
- 벽·테이블의 `<visual>` 색상 정의가 모델마다 반복된다. SDF 에는 매크로가 없어서
  줄이려면 xacro 로 SDF 를 생성하거나 모델을 파일로 빼서 `<include>` 해야 한다.
