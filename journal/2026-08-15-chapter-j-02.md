# [Chapter J] 관리형 노드 - 라이프사이클로 준비와 동작을 나누다 - 2026-08-15 (Week 07)

## 이번 주 목표
- `rclcpp_lifecycle::LifecycleNode`로 전환해 "준비"와 "동작"을 분리
- 자원 생성을 생성자에서 `on_configure`로 옮기고 `on_cleanup`에서 해제
- 비활성 상태에서 액션과 타이머가 어떻게 동작해야 하는지 결정
- I장에서 넘긴 질문 "비활성일 때 publisher와 subscription은 어떻게 관리하나"에 코드로 답하기

## 한 것
- 상속을 `rclcpp::Node`에서 `rclcpp_lifecycle::LifecycleNode`로 변경
  - `LifecycleNode`는 `rclcpp::Node`의 자식이 아니라 별개 클래스다. executor에는
    `node->get_node_base_interface()`를 넘겨야 한다
- 라이프사이클 콜백 5개 구현 - `on_configure` / `on_activate` / `on_deactivate` /
  `on_cleanup` / `on_shutdown`
- 자원 배치 정리
  - 생성자: callback group 2개만 (`create_callback_group`은 부를 때마다 새로 만들어 쌓이므로)
  - `on_configure`: publisher, subscription, service, action server
  - `on_activate`: `previous_time_` 갱신 + 타이머 생성
  - `on_deactivate`: 진행 중 goal `abort` + 타이머 해제 + 속도 0
  - `on_cleanup`: 자원 4개 `reset()`
- 비활성 상태에서 들어온 goal을 거부 (`get_current_state()`로 확인, 거부 사유가 둘로 늘었다)
- 타이머 콜백 몸통을 `on_timer()` 멤버 함수로 분리 - `on_activate`가 3줄로 줄었다
- 매직 넘버 4개를 단위 주석과 함께 멤버 상수로
  (`goal_tolerance_` m, `heading_tolerance_` rad, `max_linear_` m/s, `max_angular_` rad/s)

## 구조 - 상태와 자원의 대응
```text
Unconfigured ──configure──▶ Inactive ──activate──▶ Active
             ◀──cleanup───          ◀─deactivate──

Unconfigured : 아무것도 없음 (토픽·서비스·액션이 그래프에 안 보임)
Inactive     : 자원은 있지만 타이머가 없어 아무 일도 안 함, goal 거부
Active       : 타이머 동작, goal 수락
```

## 막힌 것 -> 어떻게 풀었나
- **`'rclcpp_lifecycle' has not been declared` - 에러 100개**: 클래스 선언만 바꾸고 배선을 안 했다.
  `package.xml`, `CMakeLists.txt`, `#include` 세 곳이 빠졌는데 에러는 100개가 쏟아졌다.
  `main()`의 `add_node`에서 "`int`를 변환 못 한다"는 황당한 에러까지 나왔는데, 전부 첫 에러의
  연쇄였다. **C++ 에러는 첫 줄만 보면 된다.** 배선을 먼저 하고 초록불을 확인한 뒤 코드를 바꾸니
  다음엔 에러가 정확히 1개만 났다.
- **`on_configure`를 헤더에서 못 찾음**: `lifecycle_node.hpp`에는 `on_activate`와 `on_deactivate`만
  있었다. 나머지 셋은 부모의 부모인 `LifecycleNodeInterface`에 있다. 그리고 `LifecycleNode`가
  하필 저 둘만 재정의한 이유는 **거기서 관리 대상 publisher를 켜고 끄기 때문**이었다. 그래서
  오버라이드할 때 부모 구현을 반드시 호출해야 한다 - 안 그러면 `/odom`이 안 나간다.
- **콜백에 `return`을 안 써서 노드가 즉사**: `[ros2run]: Trace/breakpoint trap`. 반환값이 있는
  함수가 아무것도 안 돌려주고 끝나면 컴파일러가 그 자리에 트랩 명령을 심는다.
  `-Wreturn-type` 경고 5개가 그대로 크래시 지점 5개였다. **경고는 스타일 잔소리가 아니다.**
- **`goal_handle_`이 nullptr인데 `abort` 호출 -> Segmentation fault**: goal 없이 `deactivate`하면
  죽었다. `on_timer`에는 이미 `goal_handle_ != nullptr && is_active()` 가드가 있었는데
  `on_deactivate`에는 없었다. J장에서 **같은 종류의 null 역참조로 두 번** 죽었다(`||`/`&&` 건 포함).
- **`deactivate`가 진행 중 goal을 방치**: 타이머만 껐더니 클라이언트는 영원히 대기하고, 새 goal은
  계속 `rejected`였다. 복구 방법이 노드 재시작뿐이었다. `abort(result)`로 사유를 담아 끝내고
  `reset()`하도록 고쳤다. **`deactivate`는 "잠시 멈춤"이 아니라 "지금은 일할 수 없다"는 선언**이니
  진행 중이던 약속도 정리해야 한다.
- **`activate` 순간 로봇이 7.87 m 순간이동**: 두 원인이 겹쳤다.
  (1) `previous_time_`을 생성자에서 설정해 `activate`까지 흐른 시간이 통째로 첫 `dt`가 됐고
  (2) `/cmd_vel` 구독이 생성자에 있어 `unconfigured` 상태에서도 속도 명령을 받아뒀다.
  `previous_time_`을 `on_activate`로, 구독을 `on_configure`로 옮겨 둘 다 해결했다.
  **라이프사이클을 대충 하면 어떤 사고가 나는지** 보여주는 사례라 기록해 둔다.
- **`timer_.reset()`과 `timer_->reset()`이 정반대**: 점 하나 차이로 "타이머 소멸(멈춤)"과
  "타이머 재시작"이 갈린다. `shared_ptr`은 쪽지 자체도 객체라서 `.`은 쪽지를, `->`는 쪽지가
  가리키는 물건을 다룬다. `goal_handle_.reset()`도 같은 형태다.
- **테스트가 멈춰서 버그인 줄 알았다**: `unconfigured` 상태에서 `ros2 topic pub --once`가 응답이
  없었다. 버그가 아니라 **구독자가 없어 매칭을 기다린 것**이었고, 오히려 자원 이동이 성공했다는
  증거였다. `--wait-matching-subscriptions 0`으로 해결. (I장에서도 같은 옵션을 썼었다)

## 라이프사이클에서 확인한 것
```text
상태            action  odom  reset_pose  cmd_vel구독
unconfigured      0      0        0            0
configure 후      1      1        1            1
cleanup 후        0      0        0            0
```

publisher만 프레임워크가 자동으로 막아준다 - `LifecyclePublisher::publish()`가 내부에서
`is_activated()`를 검사해 비활성이면 아무 일도 하지 않는다. 반면 **subscription, timer, service,
action은 전부 내가 직접 관리**해야 한다. I장에서 넘긴 질문의 답이 이것이다.

## 배운 것 한 줄
> 라이프사이클은 "준비"와 "동작"을 나누는 장치다. 프레임워크는 publisher만 지켜주고, 나머지
> 자원과 진행 중이던 작업의 뒷정리는 전부 내 책임이다.

## 검증
- `unconfigured`에서 액션·토픽·서비스가 그래프에 하나도 안 보임 -> `configure` 후 전부 등장 ->
  `cleanup` 후 다시 사라짐
- `activate` 전 `[timer tick]` 0개, `activate` 후 시작, `deactivate` 후 정지
- `unconfigured`에서 `/cmd_vel` 발행 후 10초 뒤 `activate` -> 첫 `dt` 0.50, 이동 없음
  (수정 전에는 `dt` 15.75에 7.87 m 이동)
- 비활성 상태에서 goal 전송 -> `Goal was rejected`
- goal 없이 `deactivate` -> 크래시 없음
- 주행 중 `deactivate` -> 클라이언트가 `ABORTED`와 사유 수신, 재 `activate` 후 새 goal 정상 수락
- 매직 넘버 정리 후에도 P 제어 수렴 비율 0.75 동일, 목표 도달 성공
