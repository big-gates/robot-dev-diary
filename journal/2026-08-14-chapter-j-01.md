# [Chapter J] 지점으로 이동 - 액션 서버와 사라지는 shared_ptr - 2026-08-14 (Week 07)

## 이번 주 목표
- 단발 요청은 서비스로, 장기 작업은 액션으로 나누는 기준을 코드로 확인
- `.action` 파일로 내 인터페이스를 직접 정의하고 빌드에 연결
- "지점으로 이동" 액션 서버 - goal 수락/거부, 진행률 피드백, 중간 취소
- I장에서 만든 callback group 구조를 액션에 그대로 재사용

## 한 것
- `reset_pose` 서비스 (`std_srvs/srv/Trigger`)
  - 포즈를 `(0, 0, 0)`으로 되돌리는 단발 요청
  - 타이머와 같은 callback group에 넣어 `pose_`에 mutex 없이 접근
- `MoveToPoint.action` 정의 - Goal `(target_x, target_y)`, Result `(success, final_x, final_y,
  message)`, Feedback `(remaining_distance)`
- `rosidl_generate_interfaces`로 인터페이스 생성, `rosidl_get_typesupport_target`으로 링크
- 액션 서버 3콜백 작성
  - `handle_goal`: 진행 중인 goal이 있으면 `REJECT`, 없으면 `ACCEPT_AND_EXECUTE`
  - `handle_cancel`: `ACCEPT` (이동은 언제 멈춰도 안전한 작업이므로)
  - `handle_accepted`: goal handle을 멤버에 저장
- 타이머를 상태 머신으로 사용 - 별도 스레드 없이 500 ms tick마다 한 걸음씩 진행
- 비례 제어(P)로 속도 생성 - `relative_bearing`으로 헤딩 오차, 남은 거리로 선속도

## 구조 - goal이 주행이 되는 순서
```text
send_goal
  -> handle_goal: 진행 중 goal 있으면 REJECT
  -> handle_accepted: goal_handle_ 멤버에 저장

500 ms timer callback
  -> goal_handle_ 살아있나?
       취소 중 -> 정지 + canceled(result)  + reset()
       도달    -> 정지 + succeed(result)   + reset()
       주행    -> relative_bearing -> 속도 계산 -> cmd_* 갱신
                  publish_feedback(remaining_distance)
  -> 명령 스냅샷 -> dt 측정 -> integrate_odom -> /odom 발행
```

액션 블록은 "명령을 정하는 일"만 하고, 실제로 로봇을 움직이는 것은 I장에서 만든 적분 코드
그대로다. 액션은 `/cmd_vel`과 같은 멤버 변수에 쓰는 또 하나의 명령원이 된다.

## 막힌 것 -> 어떻게 풀었나
- **내 패키지가 만든 헤더를 못 찾음**: `fake_robot/action/move_to_point.hpp: No such file or
  directory`. 헤더는 `build/`에 분명히 있었다. `ament_target_dependencies`는 `find_package`로
  찾은 *남의* 패키지만 연결해주고, 방금 생성한 *내* 인터페이스는 대상이 아니었다.
  `rosidl_get_typesupport_target()`으로 타깃 이름을 받아 `target_link_libraries`에 plain 문법으로
  붙이니 include 경로와 라이브러리가 한 번에 해결됐다. (검색: `rosidl_get_typesupport_target`)
- **빌드도 실행도 되는데 `ros2 action list`가 비어 있음**: `/reset_pose`는 보이는데 액션만 없었다.
  `create_server`의 반환값을 아무 데도 대입하지 않은 게 원인이었다. `callback_group.hpp`를 열어
  보니 `waitable_ptrs_`가 `WeakPtr` 벡터였다 - 유일한 강한 참조인 반환값을 버리면 세미콜론을 찍는
  순간 서버가 소멸한다. 멤버에 저장해서 해결.
- **goal이 수락되자마자 끝남**: `success=false`, `message=''`인 빈 결과가 즉시 돌아왔다.
  `handle_accepted`가 받은 goal handle을 저장하지 않아서, 콜백이 끝나며 참조가 0이 되고
  `~ServerGoalHandle()`이 "종료 상태에 도달 못 함"을 감지해 자동 취소한 것이었다. **같은 교훈을 두
  번 겪었다** - 서버도, goal도, 안 붙잡으면 사라진다.
- **취소 분기가 실행되지 않음**: `if (is_active()) ... else if (is_canceling())`로 썼는데 취소
  요청을 보내도 아무 일이 없었다. `rcl_action_goal_handle_is_active()` 문서를 보니 ACCEPTED,
  EXECUTING, **CANCELING** 셋 다 `true`를 반환한다. 즉 `else if`는 도달 불가능한 죽은 코드였다.
  `is_canceling()`을 먼저 검사하는 중첩 구조로 바꿨다.
- **노드가 첫 tick에서 Segmentation fault**: `[timer tick]` 로그가 0줄이었다. 조건을
  `goal_handle_ != nullptr || goal_handle_->is_active()`로 썼는데, `||`는 왼쪽이 false일 때
  오른쪽을 평가한다. 즉 nullptr일 때 정확히 역참조하는 조건이었다. nullptr 가드는 항상 `&&`.
- **취소했는데 그 tick에 로봇이 계속 감**: 명령 스냅샷을 액션 블록보다 **먼저** 뜨고 있었다.
  액션이 멤버를 0으로 바꿔도 이번 tick의 지역 복사본은 옛 값이라 그대로 적분됐다. 액션 블록을
  스냅샷 위로 옮겨 해결.
- **취소 후 다음 tick부터 다시 달림**: 정지를 지역 변수에만 썼더니 `x`가 2.25에서 멈췄다가
  2.50, 2.75로 다시 늘었다. 멤버 `cmd_linear_x_`에 텔레옵이 보낸 0.5가 남아 있어 스냅샷이 그걸
  다시 읽어온 것이다. **일시적 명령은 지역 변수로 충분하지만, "정지"처럼 goal이 끝난 뒤에도
  유지돼야 하는 상태 변경은 멤버에 써야 한다.**
- **도달 판정이 영영 안 남**: 목표 `(0,0)`에 이미 서 있는데도 성공하지 않았다.
  `abs(remaining - 0.5) < 1e-9`로 썼는데, 부동소수점에서 등호 비교는 맞아떨어지지 않는다.
  `remaining < 0.05`로 범위 판정으로 바꿨다. 임계값은 오차 보정 장치가 아니라 "이만큼 가까우면
  도착으로 친다"는 공학적 결정이고, Nav2에도 `xy_goal_tolerance`라는 같은 개념이 있다.
- **무슨 goal을 보내도 "목표 도달" 성공**: `ros2 node list`에 `/fake_robot`이 두 번 나왔다.
  `fake_robot_node` 프로세스가 2개 살아 있었고, 각자 다른 `pose_`를 갖고 있었다. `send_goal`은
  양쪽 서버에 goal을 보내고 먼저 응답한 쪽 결과를 받는다. 하나만 남기고 정리했다. 테스트 전에
  `ros2 action info /move_to_point`로 `Action servers: 1`을 확인하는 습관을 들였다.
  (검색: `ros2 nodes share an exact name`)
- **클라이언트를 강제 종료하니 서버가 마비됨**: 이후 모든 goal이 `Goal was rejected`. 클라이언트가
  취소를 보내지 못하고 죽으면 `goal_handle_`이 계속 active로 남고, 밖에서 취소할 수단이 없다.
  노드 재시작 말고는 복구가 안 됐다. **REJECT 방식을 고른 대가**다 - 선점(preempt) 방식이었다면
  새 goal이 막힌 상태를 밀어냈을 것이다. Nav2가 선점을 쓰는 이유에 고장 복구도 있다는 걸 알았다.

## P 제어에서 확인한 것
```text
목표 (1.0, 0.5), k_lin = 0.5, dt = 0.5

remaining: 1.118 -> 0.875 -> 0.663 -> 0.499 -> 0.375 -> 0.282
        -> 0.212 -> 0.159 -> 0.119 -> 0.090 -> 0.067 -> 0.050 -> 0.038 -> 도달

비율:      0.78 -> 0.76 -> 0.75 -> 0.75 -> 0.75 -> ...
           (첫 두 tick은 clamp(0.5)에 걸려 비율이 다름)

한 tick 이동 = k_lin * d * dt = 0.5 * d * 0.5 = 0.25d
남은 거리    = d - 0.25d = 0.75d
```

수식이 예측한 0.75가 로그에 그대로 나왔다. 그리고 이 지수 수렴 덕분에 목표에 가까울수록 스텝이
작아져서 임계값 구간을 뛰어넘지 않는다 - 고정 속도로 수동 주행했을 때 0.25 m씩 뛰며 0.05 m 구간을
지나칠 뻔했던 문제가 P 제어에서는 자동으로 사라진다.

## 액션의 정체
```text
액션 = 서비스 3개 + 토픽 2개
  서비스: send_goal, cancel_goal, get_result
  토픽:   feedback, status
```

`.action` 파일 하나로 `rosidl`이 c / cpp / py / rs 네 언어의 코드를 생성한다. 내가 쓴
`ros2 action send_goal`은 Python으로 짠 **범용** 클라이언트이고, 타입 이름을 문자열로 받아 런타임에
모듈을 로드해 내 C++ 서버와 통신한다. 액션은 C++ 문법이 아니라 ROS 2의 통신 규격이고,
`rclcpp_action`은 그 규격을 C++에서 쓰기 위한 평범한 라이브러리다. 서빙로봇 SDK의
`moveTo(x, y)`가 사실 이 구조였다.

## 배운 것 한 줄
> ROS 2에서 `shared_ptr`을 안 붙잡으면 조용히 사라진다 - 서버도, goal도. 그리고 빌드 통과는
> 동작의 증거가 아니다.

## 검증
- `ros2 action list`에 `/move_to_point`, `ros2 action info`에서 `Action servers: 1`
- 목표 `(0, 0)`: 즉시 `SUCCEEDED`, `message: 목표 도달`
- 목표 `(1.0, 0.5)`: 자율 주행으로 도달, 피드백이 1.118에서 0.038까지 감소
- 진행 중에 두 번째 goal 전송: `Goal was rejected`, 첫 goal은 계속 유지
- 취소: `status 5 (CANCELED)`, `message: 취소 완료`, 취소 후 `x`가 2.25에 고정
- `[goal 취소]`(요청 접수)와 `[goal 취소 완료]`(타이머 이행) 사이에 최대 500 ms 간격 확인
